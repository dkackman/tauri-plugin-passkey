# Adding a new plugin command

A command is not complete until every layer below has it. Missing one usually shows up
as a runtime "command not found" on a single platform, or a build failure because a
`cfg`-selected backend doesn't implement the trait.

1. Add the command name to the `COMMANDS` array in
   `tauri-plugin-passkey/build.rs`.
2. Add the `#[command]` handler in `tauri-plugin-passkey/src/commands.rs`, and register
   it in the `tauri::generate_handler![...]` list in
   `tauri-plugin-passkey/src/lib.rs`.
3. Add the method to the `Authenticator<R>` trait in
   `tauri-plugin-passkey/src/authenticators/mod.rs`. Give it a default no-op/`log::warn!`
   body there if most backends don't need to implement it (follow the existing pattern
   used by `send_pin`/`select_key`/`cancel`).
4. Implement it in each backend that needs real behavior:
   - `src/authenticators/ctap2/` (Linux)
   - `src/authenticators/macos.rs` (macOS — calls through the C FFI declared in this
     file; if the command needs new native behavior, add the corresponding
     `extern "C"` function here too)
   - `src/authenticators/mobile.rs` (iOS + Android — calls `self.0.run_mobile_plugin(...)`)
   - `src/authenticators/windows.rs` (Windows)
5. Wire the native sides that `mobile.rs`/`macos.rs` call into:
   - macOS: `macos/Sources/WebauthnBridge/Exports.swift` (the `@_cdecl` FFI entry point)
     and `macos/Sources/WebauthnBridge/PasskeyHandler.swift` (the actual
     ASAuthorization-based implementation)
   - iOS: `ios/Sources/WebauthnPlugin/WebauthnPlugin.swift` (the `@objc` Tauri plugin
     command method) and `ios/Sources/WebauthnPlugin/PasskeyHandler.swift`
   - Android: `android/src/main/java/WebauthnPlugin.kt` (add an `@Command` method;
     Credential Manager calls go through `CredentialManager.create(activity)`)
6. Export the JS/TS API in `tauri-plugin-passkey/guest-js/index.ts`.
7. Regenerate the permissions, then rebuild the JS bindings:
   ```bash
   cd tauri-plugin-passkey && cargo build   # or: cargo check
   ```
   `build.rs` (`tauri_plugin::Builder`) derives per-command permission files from
   `COMMANDS` and writes them under `permissions/autogenerated/` — this only happens
   under `cargo build`/`cargo check`, not `pnpm build` (that's rollup, JS bindings
   only) or `pnpm -r build` (vite, the test app). Check `permissions/autogenerated/`
   for the new entry and commit it. Separately, run `pnpm build` to rebuild the JS/TS
   bindings in `dist-js/` for the exported guest-js API.

If uncertain how a layer actually works, read the real file rather than guessing —
`register`/`authenticate`/`cancel` in each backend are good worked examples to copy the
shape of.

Then verify on a real device — simulators/emulators can behave differently for
platform authenticator flows (e.g. Android Credential Manager, iOS/macOS
ASAuthorization):

```bash
cd test-app && pnpm tauri [ios|android] dev
```

For desktop, `pnpm tauri dev` (Windows/Linux) or, on macOS,
`./build-macos-dev.sh && open src-tauri/target/debug/bundle/macos/test-app.app` (a
signed `.app` bundle is required — the raw binary won't pass ASAuthorization checks).
